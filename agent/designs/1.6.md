# 1.6 Vector store for memory search

Architect design, 2026-11-04. Waiting on the install answer (section 8) and "OK, build 1.6".

## 1. How it works today, and why it is slow
- Embeddings are a JSON list of floats in `summaries.vector TEXT`, plus `summaries.model` (`memory.py:38-39`). Written by `add_summary` (`:92,102`), `update_summary` (`:125-131`) and `embed_missing` (`:142-150`); deleted with the row (`:135`).
- `nomic-embed-text` gives 768 dimensions (the test fake gives 20). `ollama_embedder` normalises every vector (`:377`), so `dot()` (`:239`) is cosine similarity.
- `search` (`:223-231`) calls `summaries()`, which runs `SELECT *` and `json.loads` on every row and its 768-float vector (`:155-159`), takes a pure-Python dot product per row, sorts every row, cuts to top k, and only then applies the threshold (`sim >= threshold`, or none if `threshold=None`).
- `app.py:827` calls it with `threshold=None` and filters at `:829`; then `app.py:839-840` calls `summaries()` again just to count, parsing every vector a second time.
- Most of the 208 ms is likely JSON parsing plus the Python loop.
- Existing bug: vectors of a different length are silently cut short by `zip`.

## 2. New `vectors.py` (Phase 3 reuses it)
```
VectorStore(conn, name, backend=None)   # name matches [a-z_]+; uses the caller's connection and lock
  .backend -> "sqlite_vec" | "numpy" | "python"   .dim -> int | None
  .upsert(key: str, vec)  .delete(key)  .keys() -> set  .count()  .reset(dim)
  .search(vec, k, threshold=None) -> [(key, score)]   # top k by cosine, THEN keep score >= threshold
available() -> list of backends that import and load here; always includes "python"
```
- **Same storage for every backend:** plain table `vec_<name>(n INTEGER PRIMARY KEY, key TEXT UNIQUE, v BLOB)`, `v` float32 little-endian (sqlite-vec's own format), plus `vec_meta(name PRIMARY KEY, dim, built REAL)`.
- **Normalisation:** on write and at query time, so the score is cosine for every backend (matches today's `dot` on real data).
- **sqlite_vec backend:** `conn.enable_load_extension(True); sqlite_vec.load(conn); conn.enable_load_extension(False)` (off straight away so injected SQL can't load other DLLs). Query: `SELECT key, 1 - vec_distance_cosine(v, ?) s FROM vec_<name> ORDER BY s DESC, n DESC LIMIT ?`. Uses the scalar function over the plain table, not a `vec0` virtual table: memory.db stays readable without the extension, and `vec0` KNN is brute-force in 0.1.x anyway. Phase 3 can add `vec0` behind the same API if it passes ~50k chunks.
- **numpy backend:** float32 matrix in memory, `M @ q` with `argpartition`. Marked dirty on every upsert/delete and rebuilt from the db on the next search, so a rolled-back transaction can't leave it stale.
- **python backend (neither installed):** cached list of `array('f')` rows, loop with `dot`. The app never breaks. Without JSON parsing, expect ~30-60 ms at 1,000 rows (to be measured).
- **Picking a backend:** `backend` argument, else env var `HYBRID_AI_VECTORS`, else sqlite_vec → numpy → python. A backend that fails to import or load is logged and the next one tried. The choice is logged once in the inspector.
- **Ties / precision:** ties go to the newest key (`n DESC`), matching today's `created DESC`. float32 scores differ from today's float64 by < 1e-5.

## 3. Data: the JSON column stays the source of truth
- Nothing is moved or deleted. `summaries.vector` is written exactly as now; `vec_summaries` is a derived index that can be rebuilt any time.
- `memory.py` writes the index in the **same transaction** as the summary row: upsert in add/update/`embed_missing`, delete in `delete_summary` and when an update's embedding fails.
- `MemoryStore.__init__` runs `sync()`: compares summary ids with vectors against `vec.keys()` and adds/removes the difference.
- **Dimension:** the index takes the newest vector's dimension. A write with a different dimension (embedding model changed) calls `reset(dim)` and rebuilds from rows of that dimension; others are left out (today they give garbage scores).
- New `search`: embed the query → `vec.search(q, k, threshold)` → `SELECT` only those k rows → return `[(score, summary)]` as today.
- New `MemoryStore.counts() -> (total, searchable)` via SQL `COUNT`, used by `app.py:839-840` and `memory_check.py:20,31`. **Beyond the step's wording; needs approval.**

## 4. Migration safety (memory.db)
- **When:** first open where `vec_meta` has no `summaries` row.
- **What is backed up, and where:** `sqlite3.Connection.backup()` writes `<dir of memory.db>\backups\memory-before-1.6-<YYYYmmdd-HHMMSS>.db` (= `%LOCALAPPDATA%\HybridAI\backups` in real use). The backup API gives a consistent snapshot that includes committed WAL content, so `-wal`/`-shm` are not copied separately. The path comes from the db path, not `config`, so tests stay in `tmp_path`.
- **Backup checked:** `PRAGMA integrity_check` must be `ok`, and summaries and facts counts must equal the source.
- **If the backup fails** (disk full, permission, check fails): no tables are created. Search falls back to the python backend on JSON vectors loaded once, a warning is logged, and migration is retried next start.
- **Closed or crashed mid-migration:** `CREATE TABLE`, the index fill and the `vec_meta` row are one transaction; a crash rolls back (WAL) to the old state. Next start takes a new backup and runs again.
- **Run twice:** safe. `IF NOT EXISTS`, `sync()` only adds what is missing, no second backup once `vec_meta` exists. Step 1.9's single-copy lock keeps a second process out.
- **Rollback (preferred):** old code ignores the extra tables, so checking out the earlier commit just works. Optionally `DROP TABLE vec_summaries; DROP TABLE vec_meta;`. No data lost.
- **Rollback (last resort):** with the app closed, put the backup in place of `memory.db` and delete `memory.db-wal` and `memory.db-shm`. Loses summaries saved after the migration.
- **Time at ~1,000 summaries:**

  | Stage | Estimate |
  | --- | --- |
  | Backup of ~15 MB (JSON vectors ~15 KB each) on an SSD | ~0.3-1 s |
  | Parse and pack (~0.15 ms/row) | ~0.2 s |
  | Insert ~3 MB of blobs | < 0.1 s |
  | **Total, once** | **~1-1.5 s** |

  Runs synchronously in `__init__` at start-up (simplest).

- Bad names rejected.
- Rollback leaves numpy's cache correct.
- sqlite-vec: `load_extension` is off after loading.

**`tests/test_memory.py`:** existing tests unchanged and passing, plus:

## 7. Risks and recommendations
1. sqlite-vec DLL fails to load on some machines (pre-1.0). The fallback chain handles it; `memory_check.py` reports the backend.
2. Extension loading: verified OK in the venv (sqlite 3.45.3).
3. The derived index duplicates data (~3 MB per 1,000 summaries). Accept; removing the JSON column would be a real migration, later if ever.
4. float32 can flip a score within 1e-6 of the threshold. Accept.
5. Scalar function rather than `vec0`. Recommend the scalar function now; Phase 3 (3.1) decides on `vec0`. **Open question.**
6. ~1-1.5 s pause on the first start after the update. Accept, or move to the health-check worker (more complex).
7. `counts()` and the `app.py` change go beyond the step's text. Recommend doing them, otherwise the 50 ms goal isn't met in the real reply path.
