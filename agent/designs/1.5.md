# 1.5 Chat storage: messages as rows, index, migration with backup

Architect design, 2026-11-04. Waiting for "OK, build 1.5". All timings and sizes are estimates.

## Today and why it is slow
- **Schema** (`storage.py:22-43`): `conversations(id, title, history JSON blob, created, updated, meta)` and `turns(conv_id, seq, …, extra)` with primary key `(conv_id, seq)`. Upgrades are `ALTER TABLE` on every open (`:92-97`). First-version databases have no foreign key on `turns`, so deleting a chat leaves orphan turns. No `user_version`.
- **Read path (the main cost):** `get()` (`:119-124`) calls `load_all()` (`:100-117`), which reads every chat, runs one extra query per chat for its turns and parses every history blob, to return one chat. That is the 133 ms at 2,000 chats. No index on `updated`.
- **Write path:** `save()` (`:142-160`) runs on every reply and edit; it rewrites the whole history blob, deletes all turns and inserts them again. Writes grow with chat length.
- **Callers:** app `_load_saved`/`_save`/`_forget` (`app.py:266-296`); saves after a reply, digest, reminder, Quick Ask import, code journal, edit status; `_reload_conv` uses `get`. Phone (same process, own connection): `phone.py:118` Store, `list`, `get`, `delete`, `save`.
- **Chat ids must not change:** `memory.summaries.conv_id` (`memory.py:33`) and `memory_keep_ids` refer to them.
- `quickask.py` does not touch Store. Chats have no text search.

## New schema (`PRAGMA user_version = 2`)
- `chats(id TEXT PRIMARY KEY, title, created REAL, updated REAL, meta TEXT)` + `CREATE INDEX idx_chats_updated ON chats(updated DESC)`.
- `chat_turns(chat_id REFERENCES chats(id) ON DELETE CASCADE, seq, role, text, route, meta, stopped, at, extra TEXT JSON, PRIMARY KEY(chat_id, seq))` — same columns as today, so `_turn_from_row` and `_extra` stay.
- `chat_messages(chat_id REFERENCES chats ON DELETE CASCADE, seq, role, body TEXT, PRIMARY KEY(chat_id, seq))` — `body` is the whole model message as JSON after `_strip_images`. Images still not saved; attachment metadata stays in `chat_turns.extra`.
- **PRAGMAs:** `journal_mode=WAL`, `foreign_keys=ON` (already set), plus `synchronous=NORMAL` (safe with WAL).
- **New table names on purpose:** an older app version opening a v2 db sees an empty list (visible, harmless) instead of chats with silently missing model history.

## Operations (public API unchanged)
- **`get(id)`:** three indexed queries; well under 1 ms for a normal chat.
- **`load_all()`:** three queries total, grouped in Python.
- **`list()`:** uses the `updated` index; "last message" subquery uses the primary key.
- **`last_change()`:** reads from `chats`.
- **`save(…)`** (same signature): `BEGIN IMMEDIATE`; upsert the `chats` row (keep `created`); read stored turn rows and message bodies; upsert only changed rows; delete rows with `seq >= len(new)`. A reply writes one chat row plus ~4 rows; an edit-status change updates one turn row. The db then matches the caller's lists exactly (keeps today's "last writer wins" between desktop and phone). The read must be inside the write transaction, hence the explicit `BEGIN IMMEDIATE`.
- **`delete`:** foreign-key cascade removes turns and messages.
- **`Store(path, upgrade=True, backup_dir=None)`:** `backup_dir` defaults to `<db folder>\backups`. `phone.py:118` passes `upgrade=False`, so the phone never migrates or backs up. New fields `store.version`, `store.upgrade_note`.
- **On open:** no tables → create v2. v1 and `upgrade=True` → back up, then migrate. v1 and `upgrade=False`, or backup failed → v1 mode (current code kept as `_v1_*`, with `get` changed to a direct lookup by id). `user_version > 2` → raise, the existing handler (`app.py:270`) runs, nothing written.

## Migration: in place, in one transaction
In place is safer: SQLite makes table changes and copying atomic, and a crash before COMMIT is discarded by the WAL. A new-db-and-swap needs closing connections and renaming locked files and `-wal`/`-shm` on Windows.
1. Backup (next section).
2. Separate connection, `isolation_level=None`, `PRAGMA foreign_keys=OFF` (so `DROP TABLE conversations` doesn't cascade).
3. `BEGIN IMMEDIATE`.
4. Re-check inside the transaction: `user_version` still 0 and `(COUNT, MAX(updated))` unchanged since the backup. Otherwise roll back; retry next start.
5. Old `ALTER`s if needed (first-version dbs).
6. Create the new tables.
7. `INSERT INTO chat_turns SELECT …` joined to `conversations` (drops orphan turns; counted for the log).
8. Per chat: `json.loads(history)`, one `chat_messages` row per message.
9. Drop old tables; `PRAGMA foreign_key_check`.
10. `user_version = 2`; COMMIT.
11. `PRAGMA wal_checkpoint(TRUNCATE)` (best effort).
- No `executescript` (it commits on its own).
- **Any error** (including unparseable history JSON): roll back, stay in v1 mode, log which chat failed.
- No automatic VACUUM.

## Backup (required)
- **Method:** `sqlite3.Connection.backup` into `%LOCALAPPDATA%\HybridAI\backups\chats-v1-YYYYmmdd-HHMMSS.db.partial`. It copies page by page through the live connection, so it **includes everything still in the WAL**; no checkpoint needed, works with other connections open. Copying `chats.db` + `-wal` + `-shm` as files would not be consistent, and `-shm` is useless in a copy. Chosen over `VACUUM INTO` because it keeps the file exactly as it was.
- **Check:** `PRAGMA quick_check` = "ok"; `conversations` and `turns` row counts equal the source; then `os.replace` `.partial` → `chats-v1-<ts>.db`.
- **Free space:** `shutil.disk_usage(backup_dir).free ≥ 3 × (db + wal size) + 100 MB`.
- **If anything fails** (space, OSError, check): delete `.partial`, **do not migrate**, run in v1 mode. `upgrade_note`: "Chat storage upgrade postponed: couldn't make a backup (<reason>). Your chats work as before." Logged and shown as a composer notice.
- Stale `chats-v1-*.partial` files are deleted on start.

## Crash, running twice, rollback, time
- **Crash during the backup:** `.partial` left, deleted next start; db untouched.
- **Crash during the migration:** uncommitted transaction discarded on next open; `user_version` still 0; next start backs up and migrates again.
- **Crash after COMMIT:** db is v2 and complete.
- **Running twice:** `user_version == 2` → no migration, no backup. A second process re-checks under `BEGIN IMMEDIATE` and skips.
- **Rollback:**
  1. Close Hybrid AI.
  2. In `%LOCALAPPDATA%\HybridAI`, move `chats.db`, `chats.db-wal`, `chats.db-shm` into `backups\after-1.5\` (don't delete: they hold chats made since the upgrade).
  3. Copy `backups\chats-v1-<ts>.db` to `%LOCALAPPDATA%\HybridAI\chats.db`.
  4. Check out the commit from before 1.5 (the 1.5 code would just migrate again).
  Chats made after the upgrade are lost unless copied over by hand.
- **Time and size at ~2,000 chats** (~20 turns + 20 messages per chat at ~1 KB → ~80k rows, ~80 MB): SSD backup < 1 s, migration ~1–2 s, **2–4 s total**; hard disk 5–10 s. Real data is likely much smaller (finished chats are summarised and deleted). Runs on the main thread in `_load_saved` before the main loop, so no progress bar; a log line before and after. If the laptop measurement is over 3 s, revisit with a worker thread. Measure `Store.get` on the laptop before and after.
- **1,000 summaries:** memory.db is not touched by this step.

## Tests (new `tests/test_storage.py`, `tmp_path` only)
1. **Round trip:** v1 dbs with both the first-version and current schema; chats with attachments metadata, notes, edits with status, memory, `via`, `stopped`, route/meta, `at=None`, note turns, a system message, a stripped-image note, a digest in meta, unicode/emoji, an empty chat, one orphan turn. v1 `load_all()` == new `load_all()` for every chat (ids, order, timestamps). `user_version == 2`, old tables gone, orphan gone, backup exists and equals pre-migration data.
2. **Crash mid-migration (real process death):** subprocess runs the migration with a hook that calls `os._exit(1)` halfway through message rows. Reopen: `user_version == 0`, old tables and counts intact. Rerun: migrates, second backup.
3. **Error mid-migration:** hook raises → rollback, v1 mode, `save`/`get` still work.
4. **Backup failure refuses migration:** low free space via `shutil.disk_usage`, and separately `_backup` raising `OSError` → `version == 1`, no new tables, no `.partial`, note mentions the backup, saving still works.
5. **Running twice:** open, close, open → no second backup, data identical.
6. **Incremental saves:** append 2 turns + 2 messages to a 50-turn chat → `total_changes` delta ≤ 5; edit-status change updates exactly one row; shortened chat deletes its tail.
7. **Speed:** 2,000 synthetic chats of 20+20 rows; median of 20 `get(random id)` < 50 ms, on a fresh v2 db and after migrating a v1 db.
8. **Phone:** `upgrade=False` on a v1 db stays v1 with no backup; `delete` cascades.
9. Existing `test_storage_*` and `test_phone` keep passing.

## Risks and open questions (recommendation)
1. **1.4 bug: masked counts are never saved.** `app.py:762` sets `turn["masked"]`, but `_extra` (`storage.py:58`) only keeps attachments/notes/edits/memory/via, so the counts vanish on restart. *Add `"masked"` to `_extra`, as a 1.4 follow-up or inside 1.5, with your OK.*
2. **The backup keeps full text of chats later summarised and deleted** (conflicts with "summary only"). *Auto-delete the migration backup after 30 days once v2 has opened fine (needs your OK); otherwise keep it and show its path in the Log tab.*
3. **No VACUUM**, so the file doesn't shrink. *Accept; space is reused.*
4. **Two code paths (v1 fallback mode).** *Keep v1 mode only until Phase 2, then remove.*
5. **Startup freeze on very large dbs.** *Measure on the laptop; worker thread only if > 3 s.*
6. **Old app on a v2 db shows an empty list.** *Document rollback in RUNBOOK.*
7. **Dependency on 1.9:** safe without it (re-check under a write lock); 1.9 removes the risk of two copies each making a backup.
